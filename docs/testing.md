# Testing Pipeline Sentinel

Pipeline Sentinel separates **software correctness** from **model quality**. The tests in `tests/`
are intentionally small and deterministic; benchmark datasets belong under `benchmarks/` and answer
different questions.

## Fast local acceptance run

From PowerShell at the repository root:

```powershell
uv sync --group dev
uv run ruff check .
uv run pytest
uv run pipeline-sentinel demo --output outputs\acceptance
```

Then confirm that these files exist and are non-empty:

```text
outputs/acceptance/run/annotated_video.mp4
outputs/acceptance/run/alerts.csv
outputs/acceptance/run/run_manifest.json
```

The exact output layout is generated by `run_demo`; use the printed CLI paths as the source of truth
if that layout changes in a later version.

## Current automated test layers

### Data contracts

`test_types.py` verifies that canonical types serialize and expose normalized coordinates as
expected.

### Synthetic source generation

`test_synthetic.py` verifies that the deterministic EO-like demo video is written, contains the
expected scenario labels, has the requested frame count, and produces the same annotation sequence
for the same seed.

### Ingest

`test_ingest.py` verifies that OpenCV sampling produces the expected frame numbers, timestamps,
sensor metadata, and a valid frame manifest.

### Manifest failure handling

`test_manifest.py` verifies both a valid manifest and deliberately broken manifests. A validator is
not useful if tests only prove that good input passes.

### Detector contract

`test_detectors.py` verifies the deterministic ground-truth test backend emits normalized
`Detection` objects and rejects malformed annotation schemas.

### End-to-end application smoke test

`test_pipeline.py` executes the deterministic reference pipeline, writes the annotated video,
alerts CSV, and run manifest, and checks that the manifest reports the expected backend and frame
count.

### COCO preparation regression

`test_coco_subset.py` uses a tiny synthetic COCO fixture to prove that category filtering and image
selection are deterministic without downloading the real COCO dataset in CI.

## Why the tests do not download models

CI should not unexpectedly download YOLO, DINOv2, MobileNet weights, COCO images, or other large
external artifacts just to determine whether the core package is healthy.

Heavy backends will get their own optional/integration test path. The default CI contract stays
fast, deterministic, and network-light.

## GitHub Actions

The CI workflow performs:

```text
checkout
-> install Python
-> install uv
-> uv sync --group dev
-> ruff check
-> pytest
```

A failing CI run should be treated as a repository-level regression even when a notebook still runs
successfully on one workstation.

## Model evaluation is separate

When a real detector backend is added, model-quality evaluation will live under `benchmarks/`.
Software tests ask whether the detector adapter obeys the contract. COCO/UAVDT evaluations ask
whether the detector is any good.

That distinction prevents a low model score from looking like a software crash, and prevents a
perfectly functioning adapter from being mistaken for a capable model.
